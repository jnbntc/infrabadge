# M3.5 — propuesta de interfaz y navegación

Ocho páginas200×200,1bit,5000B; fuente original M1 5×7 escalada para estado.
Cabecera y pie de alto contraste, texto ASCII soportado, máximo3 nodos por
página. Imágenes siempre **SIM/HORA SIMULADA**, nunca observaciones reales.
[Galería offline](m35-ui/index.html), sin servidor, scripts externos o red.

| Vista | Contenido propuesto |
| --- | --- |
| Resumen | Estado global, conteos y disponibilidad de CASA/TRABAJO |
| CASA | Nodos, estado y edad acotada; no edad por segundo |
| TRABAJO | UNKNOWN, SIN NODOS INCORPORADOS/NO CONFIGURADO; sin inventar nodos |
| Móviles | Métricas y edad del móvil, diferenciando ausencia de telemetría |
| Detalle | Nombre lógico, CPU/RAM/disco usados, temperatura CPU oN/A, edad |
| Alertas | CRITICAL antes de WARNING, después OFFLINE/UNKNOWN; páginas acotadas |
| Caducados | OFFLINE/UNKNOWN, edad y etiquetas históricas; sin valores actuales |
| Ambiente local | Temperatura/humedad SHTC3, CRC/validez; distinto de CPU remota |

Trece fixtures: ocho vistas más global HEALTHY/CRITICAL, gateway inaccesible,
reloj desconocido y ambiente ausente. Datos de laboratorio ficticios; ninguno
proviene del inventario privado de Core/NAS/notebook. El prototipo máximo3 nodos
no es el límite futuro del Core: el firmware definitivo requerirá paginación.

## BOOT/PWR: diseño, no conducta instalada

- BOOT corto, despierto: avanzar; debounce30ms, evento único al soltar.
- BOOT largo≥1200ms, despierto: volver a resumen al soltar; no emitir además corto.
- BOOT mantenido al wake: ignorar primera liberación, después armar navegación.
- PWR: sin evento UI; conservar función eléctrica/latch y wake existentes.
- Dormido: no hay procesamiento normal de UI. La primera pulsación despierta;
  render/consulta posterior requiere tiempo y debe distinguir causa EXT1/timer.
- No mantener BOOT durante reset/encendido: es GPIO0 de strapping.

Conflicto a resolver ANTES de firmware: M3 espera2s al arrancar y, si detecta
BOOT pulsado, abre ventana de provisión USB. Una pulsación de navegación tras
wake no debe disparar esa función. Reservar provisión a modo mantenimiento
explícito y USB bajo autorización; diseño/gesto definitivo y tests de wake
deben aprobarse aparte. No se cambia esta conducta en la placa actual.

## Render y potencia

Reutilizar HAL, framebuffer diff y scheduler/Power Manager. Full refresh
exclusivamente, intervalo mínimo existente5s (política UI, no certificación del
fabricante). Agrupar pulsaciones durante refresco, conservar última vista y
presentarla cuando termine BUSY; no encolar una transferencia por pulsación.
Errores de panel invalidan cache y detienen secuencia, sin actualizar estado
como si el draw hubiera sido exitoso. Ningún bucle de refresco continuo.

El prototipo prueba igualdad de frames dentro del mismo bucket de edad; no
implementa SPI, BUSY, ghosting, PM o flash/NVS. Cambiar de página no debe provocar
radio o escritura NVS en cada clic; futuro estado UI en RTC con CRC, invalidado
tras reset inesperado. Ventana despierta breve configurable y retorno a sleep;
su duración/energía se decidirán con medición, no se supone gratis navegar.
Presupuesto inicial: dos buffers de5000B (actual/cache) y modelo acotado; no
almacenar un framebuffer por vista ni habilitar PSRAM sin necesidad. Navegar
primero por datos cacheados vigentes; si falta una página, mostrarlo y limitar
su consulta explícita, sin descargar catálogos ilimitados por cada pulsación.

## Reproducción

```sh
python3 tools/m35/preview.py --check
# Sólo para actualizar deliberadamente referencias después de revisar el diseño:
python3 tools/m35/preview.py --update
```

PNG reutiliza el codificador stdlib de `tools/simulate_ui.py` y los glyphs de
`assets/ui-font5x7.json`; no dependencia gráfica nueva ni driver del proveedor.
No reemplaza al renderer C M1/M3 validado. Portar estas vistas será un commit
futuro con pruebas C/ASan, protocolo y siete perfiles SDK, antes de pedir carga.
