# M3.5 — firmware y edge funcionales en software

## Arquitectura efectiva

El nuevo perfil `multisite` selecciona `main/m35_main.c` y el componente
`m35_ui`. Reutiliza HAL V2, sensor/CRC, Wi-Fi STA, HTTPS TLS1.2, configuración
M2, fuente M1, display manager y Power Manager. M0/M1/M1.1/M2 conservan sus
perfiles, protocolo y comportamiento. Audio, micrófono, LED, touch y OTA quedan
fuera. No se incorpora ninguna dependencia nueva.

El Core implementa `GET /api/v2/devices/{id}/status`, una proyección del mismo
SQLite, no otro gateway ni inventario histórico. Requiere token device y,
cuando está configurado, token edge con scope para ese dispositivo. Cada
identidad device debe habilitar `presentation_v2=true`; lectores y collectors
no pueden usar sus credenciales para leerla. El edge existente admite esa ruta
sólo con `presentation_v2=true`, origen fijo, Host exacto y dos identidades. No
expone ingestión, inventario ni administración. V1 continúa disponible.

No hay despliegue LAN ni acceso a Core/NAS en esta implementación. El antiguo
gateway M3 de Fedora no se utiliza ni se repara.

## Contrato v2 acotado

Una representación atómica contiene hasta **3 sitios, 6 nodos, 4 alertas** y
`more_alerts`, máximo **4096 bytes ASCII**. Exceder capacidad produce 503, no
truncado silencioso de nodos. Las alertas se ordenan CRITICAL antes de WARNING;
se derivan de los latches de salud existentes, no de un pico aislado. Los sitios
vacíos conservan UNKNOWN y cero nodos; ningún placeholder representa un equipo.

Campos raíz: `schema_version=2`, `device_id`, `revision`, `generated_at`,
`expires_at`, `status`, `sites`, `nodes`, `alerts`, `more_alerts`. Ver modelos
Pydantic en `distributed/presentation.py` y decoder C en `m35_ui/decode.c`.
Los porcentajes son enteros en décimas (0–1000), temperatura CPU en centésimas
(-4000–15000), ausencia JSON null. `sampled_at` permite mostrar edad incluso
cuando la muestra ya caducó; `valid_until=null` implica métricas null y estado
UNKNOWN/OFFLINE. Temperatura local SHTC3 es independiente y nunca viaja al Core.

El decoder rechaza campos extra/duplicados, IDs incoherentes, estados agregados
inconsistentes, métricas caducadas no nulas, fechas futuras, tamaños/cardinalidad,
profundidad >8 y más de 256 aperturas/separadores estructurales antes de cJSON.
No hay buffers dimensionados por el servidor. El framebuffer tiene 5000 bytes;
una aserción de compilación limita la estructura RTC completa a 7680 bytes.
No se habilita PSRAM ni se modifica el mapa de particiones.

La revisión v2 persiste en la tabla `snapshots` existente bajo una clave prefijada;
no requiere migración de esquema SQLite. Edad sola no cambia representación.
ETag SHA-256 por bytes, If-None-Match y 304 conservan el vencimiento original.
`X-InfraBadge-Expires` permite al edge rechazar incluso un 304 vencido sin caché.
El próximo timer no se programa después de expires_at si la cache sigue vigente.
La caducidad se reevalúa por UTC aunque los bytes no cambien. Un fallo de consulta
no es evidencia de que todos los nodos hayan caído: se muestra SIN CONEXION y sólo
pueden mostrarse métricas de cache todavía vigentes. Tras vencimiento, se ocultan.

## Pantallas y navegación

1. Resumen: salud, cinco contadores, sitios/nodos, alerta prioritaria y edad.
2. Sitios: CASA/MOVIL/TRABAJO según nombres lógicos configurados y sus scopes.
3. Nodo: recorre cada nodo, CPU/RAM/disco/temperatura, edad y ausencia/caducidad.
4. Alertas: hasta cuatro filas con nodo, severidad, métrica, valor y edad.
5. Ambiente: SHTC3 local, lectura válida o N/A.

BOOT corto avanza; en detalle recorre nodos antes de pasar a alertas. BOOT largo
(>=1200 ms, decisión al soltar) vuelve a resumen. Rebote de 40 ms. PWR no navega,
conserva circuito y wake. Un botón mantenido al despertar queda desarmado hasta
soltarlo: esa pulsación despierta, la siguiente navega. El primer gesto no se
interpreta como una provisión USB. Los nombres `_` se muestran con `-` para
reutilizar sin cambios la fuente M1; los IDs del protocolo no se alteran.

Ventana interactiva tras wake por botón/cold boot: 20 s desde el último gesto,
máximo 120 s; timer wake no mantiene un menú residente. Sin transferencias
continuas: se renderiza por gesto, cambio de minuto/validez o aplazamiento de
pacing. Display manager compara los 5000 bytes, sólo refresco completo y mínimo
5 s entre frames distintos. Vista, snapshot, ETag y framebuffer se conservan en
RTC con CRC y hash CRC de configuración; sólo se restauran tras deep sleep válido.
Cold reset invalida esa retención y confianza temporal. No se escriben snapshots
v2 ni navegación continuamente a NVS.

La imagen e-paper puede sobrevivir a una caída de alimentación. `VENCE` indica
el límite de los datos dibujados, no prueba actividad MCU ni precisión de wake.
Navegar durante sueño requiere despertar y el tiempo de refresco completo.

## Reloj y provisión futura

No se usa RTC PCF85063/2056 como UTC. Se conservan lease de una hora, verificación
CA/SAN/fechas y continuidad RTC del ESP32. Tras cold reset, el perfil ofrece una
ventana USB de **10 s**, sin gesto BOOT, mediante el protocolo existente IBPROV1.
Sólo un paquete privado validado del host solicita guardar configuración/UTC;
sin paquete no hay escritura automática ni borrado. Los retornos de deep sleep
no abren ese driver. No se han enviado paquetes ni flasheado esta versión.

Cambiar URL/CA/token y renovar UTC en una prueba física requiere autorización
específica. La escritura por provisión sustituye la configuración M2 y elimina
su snapshot v1 mediante el mecanismo existente; no equivale a borrar NVS entera.
Conservar el archivo privado anterior antes de autorizar esa operación.

## Pruebas y reproducción

```sh
# SDK fijado; sin puertos ni flashing: siete anteriores + M3.5
bash tools/build-m35.sh --all
# En el venv gateway con los locks existentes
PYTHONPATH=gateway:tools/m32 python tools/m35/wire_fixtures.py --check
python tools/m35/firmware_visuals.py --check
python -m pytest -c pytest.ini
bash tools/m3/check_style.sh
```

El job gateway de CI compila primero el ejecutable nativo con la imagen SDK
fijada. Así el test Core → edge → parser C → framebuffer ejecuta el código de
producción. Los jobs Python ARM64 no requieren un ejecutable x86: las pruebas
que necesitan ese artefacto se omiten explícitamente allí. Sanitizadores y
regresión C se ejecutan en el job SDK. [Capturas C](m35-firmware-ui/index.html)
no son las antiguas maquetas Python ni una validación óptica. Aunque el renderer
imprime REAL, todos los datos de estas capturas son fixtures sintéticos.
