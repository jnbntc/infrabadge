Fecha: 23/10/2026. Estado: **conectividad, resumen y navegación confirmados; ambiente y recuperación en comprobación**. No equivale a validar toda M3.5 ni el consumo.

## Artefacto instalado y conservación

`902645be8f1d5f7ce3049f8620edee42c19108b832bb5fb0179a6204506cf1d3`.

Bootloader, tabla, backup privado de fábrica y rollback normal M3 se conservaron.

Encryption, OTA ni cambios de periféricos/GPIO. Las provisiones aceptadas actualizan
la configuración normal `ib_m2`; esa operación puede eliminar la antigua clave de
snapshot v1 según el store existente y no equivale a preservar todo el contenido
previo de NVS. No se restauró fábrica ni M3.

## Correcciones y límites de diagnóstico

Los intentos previos se conservaron. Se corrigieron la búsqueda de módulos del
adaptador en el contenedor (`PYTHONPATH=/app`), los identificadores AKI/SKI de la
hoja TLS, la recarga de la unidad generada y el uso de una dirección cableada ya
caducada. El lanzador comprueba ahora la IP vigente dentro del mismo perfil y
subred aprobados, repite TLS local y verifica la unidad antes de pedir sudo. Si
cambia perfil/subred o hay direcciones ambiguas, se detiene. No modifica DHCP.

El timeout Wi-Fi20000ms era un error de la configuración preparada para el ensayo;
el firmware sólo admite1000–15000ms. Se comprobó con su parser exacto y se añadió
validación host de los rangos de intervalo, Wi-Fi y HTTP antes de abrir USB.

Durante el fallo de conexión había dos interfaces del host activas en la misma
subred, mientras la guardia sólo aceptaba la cableada. Tras desconectar Wi-Fi y
estabilizar el transporte, el dispositivo obtuvo dos HTTPS200 con la misma CA,
URL, token y aplicación. La selección de entrada/ARP entre ambas interfaces es
una explicación compatible con lo observado; no se capturaron paquetes ni se
leyeron los contadores privilegiados que permitirían atribuir cada descarte.
No se desactivó la validación TLS ni se amplió la guardia a otras interfaces. La comprobación privada del SSID confirmó que la red aprovisionada era la misma del perfil Wi-Fi de laboratorio del host; no se publicaron sus datos.

La primera comprobación inmediata tras desconectar Wi-Fi falló y restauró la
conexión; la segunda dejó un plazo de estabilización y pasó. No se reescribe el
primer intento como satisfactorio. El commit host `f61a1cd` se publicó en la rama del PR; sus377 pruebas locales pasaron. El firmware instalado sigue siendo el pack original.

Una renovación USB fue inicialmente bloqueada
por revisión automática de permisos; no se ejecutó hasta la autorización específica.

## Operación y rollback

Fedora debe permanecer encendida y con su gestor de usuario disponible. El edge
utiliza el Core mediante HTTPS privado sobre Tailscale; la configuración de esa
VPN se conserva. No se habilitó linger. El guardia cierra la publicación si cambia
la dirección, interfaz o perfil aprobados. No hay reserva DHCP/DNS nueva ni promesa
de recuperación automática del listener si cambia la IP: requeriría actualizar
el plan, la hoja/URL y, si cambia la URL del dispositivo, autorizar su provisión.

Para rollback se conserva la app M3 de863472B, SHA
`9311046ba985e95a285404b6824ab3c9ec8da1eebe2003fa007656b4d75debcc`,
compatible con la tabla existente, junto con la configuración previa privada.
Una restauración de aplicación no restaura automáticamente NVS ni acredita que
el antiguo gateway localhost M3 funcione; esa ruta de entrega tenía una limitación
preexistente. No ejecutar un plan de carga/provisión consumido ni restaurar toda
la flash. El rollback del Core debe preservar la base SQLite y las muestras
posteriores al despliegue; el watchdog provisional no revierte una instalación ya
confirmada. Ver el [plan de ensayo y rollback](M3.5-PHYSICAL-PLAN.md).

La ventana interactiva no consulta continuamente la red. Si el snapshot vence durante la navegación, se muestra DATOS CADUCADOS y las métricas dejan de presentarse como vigentes. Al dormir con un snapshot ya vencido, la política actual puede usar el intervalo configurado900s; no se promete una recuperación inmediata sin otra consulta. Un BOOT breve después de la ventana sin actividad permite solicitarla manualmente. Esta limitación queda documentada, sin alterar firmware en el cierre.
