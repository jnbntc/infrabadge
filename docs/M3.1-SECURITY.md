# M3.1 — amenazas y límites

Candidato no desplegado; no es certificación ni pentest. Conserva los límites de
[SECURITY](SECURITY.md) y [auditoría M3](M3-AUDIT.md). No cambia dependencias,
firmware, cifrado NVS, eFuses o mecanismos de confianza temporal.

| Amenaza | Mitigación candidata | Límite |
| --- | --- | --- |
| Cliente LAN no autorizado | TLS1.2 mínimo, CA/SAN/fechas, bearer por dispositivo y comparación existente | No mTLS; token robado permite consultas de esa identidad |
| Collector remoto inyecta estados | Entrada LAN sólo GET status, ingreso sólo loopback, tokens distintos | Mismo usuario/root o collector comprometido fuera de protección |
| Red o IP equivocada | IP host exacta, política NM/SSID/interfaz/firewall/DNS, permiso15s | No autentica criptográficamente la Wi-Fi; SSID es falsificable |
| Cambio de red durante consulta | Comprobación antes de petición y cabeceras; caducidad CLOCK_BOOTTIME | Ventana hasta15s, sockets TLS siguen accesibles, bytes enviados no se revocan |
| Peticiones abusivas | Global120/min burst20; dispositivo6/min burst2; identidades finitas | Un atacante puede consumir cuota global y provocar denegación |
| Recursos agotados | Cabeceras8192B, token103B, sin body/query/encoding, espera body2s; Uvicorn concurrencia16, keepalive2s, shutdown5s | Cuotas son HTTP, no limitan handshakes; rate limit kernel/perimetral pendiente |
| Permisos de red excesivos | Regla precisa requerida, rechazo de puerto explícito amplio, hash reglas revisadas | No audita todas las zonas, políticas globales/servicios o router; revisión humana obligatoria |
| Pérdida del collector/cache | TTL original, UNKNOWN, recuperación siguiente muestra | Histéresis/antireplay/caché en RAM se pierden al reiniciar |
| Datos privados en logs | Telemetría fija agregada RAM, sin access logs ni payloads, archivos0600/0700 | journald/systemd pueden incluir rutas/errores locales; no publicar logs crudos |
| Contenedor comprometido | Rootless UID10001, sin capacidades, RO, no-new-privileges, mounts mínimos | Lee tokens/digests y clave TLS necesarios; no protege contra mismo UID/root |

## Límites de exposición

Sólo publica IPv4 seleccionada y loopback; IPv6 y otras IP no se publican. El
bind de IP **no liga por sí solo paquetes a una interfaz física**. Exigir firewall
ligado al perfil y probar en host real. No atribuir a tests ASGI/loopback la
ausencia de exposición real. No host network, wildcard host, proxy/Forwarded
confiable, redirección, endpoint público de métricas ni control remoto de comandos.
No abrir gateway en Internet/UPnP ni instalar excepciones VPN globales.

El guard utiliza sólo herramientas de lectura existentes; falta de permiso o
timeout deniega. No contiene sudo ni verbos de configuración. El hash del firewall
es referencia de una revisión, no una prueba de aislamiento. La consulta de ruta
representativa no cubre políticas por cliente. Cualquier despliegue real necesita
verificación de retorno y filtros efectivos, con rollback exacto aprobado.

La entrada local sigue disponible con el permiso LAN vencido. Para arrancar el
candidato se exige un permiso válido; si el arranque falla no se sustituye TLS ni
se abre un bind alternativo. Reconexión no conserva muestras caducadas como frescas.

## Rotación de credenciales

Collector y dispositivo siguen separados. Generar tokens aleatorios fuera de Git,
sin argv, shell history o logs; guardar sólo digests en gateway. La configuración
existente admite transición con más de un digest dentro de sus límites. Preparar
nueva configuración privada, autorizar reinicio del único gateway, cambiar el
cliente por canal local privado y comprobar acceso; retirar digest anterior tras
confirmación. Rotar token del ESP32 requiere provisión USB aparte, sin flasheo.
No reusar su token para probar desde otros clientes como si fueran evidencia física.

Reinicio del gateway pierde evaluación/cache RAM. Verificar UNKNOWN y recuperación
después de toda rotación; conservar backup privado para rollback. Un token extraído
de NVS no cifrada no queda protegido por permisos del host. No anunciar resistencia
a extracción física, Secure Boot o Flash Encryption.

## Renovación TLS

Inspeccionar vencimiento con antelación (propuesta operativa:30d/7d) y registrar
sólo fecha/estado saneados. No hay servicio automático de renovación instalado.
Con CA cuya clave se custodia fuera del gateway, emitir leaf con ambos SAN
localhost y hostname LAN, vigencia adecuada y key usage, probar cadena y fechas,
reemplazar par completo de manera controlada y reiniciar tras autorización.
La CA de laboratorio M3 perdió deliberadamente su clave de firma; ese camino
no está disponible con ella. Migración a CA nueva implica aprovisionamiento
confiable del ESP32 autorizado aparte. Preservar CA anterior durante rollback
si corresponde; el firmware actual no obtiene trust anchors de la red.

Nunca usar verify=false, CA global del host añadida automáticamente, certificado
vencido aceptado o fecha del RTC2056 para resolver un fallo. UTC de host confiable
para provisión inicial; reset frío interrumpe continuidad temporal del ESP32.

## Evidencia y privacidad

Tests usan red, UUID, certificados y tokens ficticios. La política y bundle reales
son privados: incluso hashes SSID/direcciones/UUID no deben publicarse. El contexto
de imagen usa allowlist y no incluye tools, docs, policy/configs privadas o results.
La telemetría cuenta consultas autenticadas, no identifica físicamente al MCU ni
demuestra deep sleep, reset/wake, framebuffer sin transferencia o autonomía.
Mediciones eléctricas continúan **DEFERRED** por decisión del usuario.
