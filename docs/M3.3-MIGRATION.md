# M3.3 — propuesta de migración reversible

**No ejecutar todavía.** Las fases A/B/C terminaron con evidencias y candidatos
privados. La autorización de lectura del core no autoriza esta migración.
Ver [arquitectura](M3.3-ARCHITECTURE.md) y [preflight](M3.3-FEDORA-PREFLIGHT.md).

## Diferencias exactas previstas

| Archivo/componente | Cambio propuesto | Conservado |
| --- | --- | --- |
| Collector JSON existente | node_id, gateway_url, ca_file, state_file | Montaje, label, intervalo 60s, timeout 10s; sin delivery_attempts nuevo |
| collector.token existente | Credencial nueva de este nodo, 0600 | Copia privada del token M3 anterior para rollback |
| CA en subdirectorio privado M3.3 | Copiar certificado público central ya existente | CA/leaf/clave de M3 y PKI central originales |
| Baseline M3.3 | Archivo distinto, inicialmente sin delta | Baseline M3 original |
| Zipapp, Python, servicio y timer | **Sin edición ni actualización** | Código M3 validado, LoadCredential, límites y cadencia |
| Core config privado | Añadir un Node mobile y su identidad collector | Otros nodos, scopes, políticas, readers y límites |
| Firewall propio del core | Una aceptación exacta notebook/32→core/32 TCP9443 en tailscale0 antes del descarte | Permiso remoto anterior, denegaciones, SSH y otras reglas |
| Gateway local M3 | Sin cambio | Imagen, Quadlet, config, claves, evidencias; fallo actual visible |

La identidad no tendrá permisos de reader/device/edge. No se necesita un nuevo
certificado servidor: SAN y CA actuales son adecuados. No se copia la clave CA
al core ni a la instalación del collector. El token se genera después de aprobar,
se entrega por archivos privados/stdin y sólo su digest entra al inventario.

## Preparación inmediatamente anterior a cualquier cambio

1. Releer versiones, estados y hashes privados del preflight. Abortar ante drift,
   identidad ya existente, dos collectors, reloj no confiable o cambio de origen.
2. Registrar configuración y enabled/active de las unidades. Crear backup nuevo
   0700/0600 de config/token/CA/zipapp/unidades afectadas, con propietarios,
   permisos y hashes; no copiarlo a Git ni sobrescribir informes anteriores.
3. En el core, backup SQLite mediante la CLI existente `backup`, que usa la API
   SQLite de copia coherente del writer activo. Validar restauración a destino
   nuevo, esquema/integridad y referencia de backup. No usar cp sobre la DB viva.
4. Revisar los tres permisos por separado: aplicación, firewall y Grants.
   No ampliar Grants automáticamente ni inferir exclusividad de toda la tailnet.
   La revisión del control plane queda pendiente; si exige cambios, detenerse y
   pedir otra autorización con su diff.

## Orden de aplicación propuesto, sólo tras autorización

1. Parar únicamente el timer Fedora y esperar que su oneshot quede inactivo.
   No disparar un segundo proceso manual en paralelo. Capturar si era enabled.
2. Preparar token nuevo y config privada; validar esquema/diff sin iniciar Core
   contra la DB viva. Ficheros del core deben conservar UID/GID y 0600 actuales.
3. Preparar y revisar el archivo propio del firewall. Revalidar por expresión el
   handle de descarte9443, no reutilizar un número antiguo. Comprobar con nft -c
   en el entorno autorizado e insertar **una sola** regla antes del descarte;
   registrar su handle/comment/expresión. Instalar sólo la edición persistente
   revisada. No ejecutar flush ruleset ni restart del servicio de firewall.
4. Verificar desde Fedora TLS real con CA/nombre/fecha. Ante rechazo, no enviar
   credenciales ni desactivar verificaciones; retirar únicamente la regla nueva.
5. Instalar el alta validada en el inventario y reiniciar únicamente
   `infrabadge-m32-core.service`. No tocar socket ni timers, hacer daemon-reload
   global o detener el gateway para simular fallos. No se modificaron unidades.
6. Confirmar nodo nuevo UNKNOWN/never y existentes históricos hasta su siguiente
   muestra. Tras el reinicio, comprobar ambos nodos anteriores frescos; abortar
   si no se recuperan dentro de sus políticas. No prometer HEALTHY continuo.
7. Sustituir config/token Fedora atómicamente con timer parado. Mantener el
   mecanismo LoadCredential y arrancar un solo oneshot; luego reactivar el timer
   original. Evitar muestras nuevas separadas por menos de 30s; si se necesita
   otra ejecución manual, esperar al menos 31s y coordinarla con el timer.
8. Confirmar dos muestras reales nuevas, CPU warmup/delta, último resultado,
   unicidad del proceso y avance independiente de los tres nodos. Preservar los
   journals, sin reset-failed para simular un historial limpio.

El reinicio es necesario: no existe recarga en caliente del inventario. Una
actualización sin interrupción requeriría otro diseño, fuera de A/B/C. La DB se
conserva, pero el nuevo proceso no presenta muestras restauradas como actuales.

## Comandos y datos privados

El informe privado identifica rutas, UID/GID, hashes, destino, origen y diff de
una regla con direcciones reales. Los ejemplos públicos no son inventario:

```sh
# Consulta previa; no concede permisos
systemctl --user show infrabadge-collector.service infrabadge-collector.timer
systemctl --user list-timers infrabadge-collector.timer
# Después de autorizar y revisar los archivos privados:
systemctl --user stop infrabadge-collector.timer
# Esperar inactividad; luego sustitución privada atómica y un solo arranque
systemctl --user start infrabadge-collector.service
systemctl --user start infrabadge-collector.timer
```

No ejecutar el instalador M3: rechaza una instalación existente y no es una
herramienta de migración. No crear una segunda unidad, instalar pip global,
activar linger, tocar rpm-ostree, VPN, NetworkManager, DNS, rutas o el ESP32.

## Autorizaciones aún necesarias

- Cambio del collector/config/credencial y control acotado de su timer/oneshot.
- Backup coherente, alta de inventario y reinicio corto del core; sin alterar NAS.
- Regla nueva y edición persistente propia del core, exclusivamente para 9443.
- Grants, si se propone cambiarlos: aprobación separada, todavía sin diff.
- Pérdida de transporte de prueba, suspensión, redes, logout o reboot: escenarios
  independientes descritos en [MOBILITY-VALIDATION](M3.3-MOBILITY-VALIDATION.md).

La reparación del gateway M3 fallido tampoco está incluida. Su límite de rollback
debe aceptarse o resolverse con otra autorización; [procedimiento](M3.3-ROLLBACK.md).
