## Timeout, retry y CPU verificados en el código instalado

El zipapp hace un POST por oneshot, sin retry, proxy de entorno, redirects o spool.
El deadline HTTP de10s cubre DNS/conexión/request/read; TimeoutStartSec20s limita
el servicio completo. Timer:60s tras terminar, coalescing5s, Persistent=false y
WakeSystem=false. No se cambia esa política para hacer pasar el ensayo.

Durante F la adquisición y el guardado del baseline ocurren ANTES del POST fallido.
Por tanto, se espera que CPU conserve delta válido si los gaps son menores que180s.
**No exigir warmup sólo porque falló la red.** Si aparece un gap real, exigir
cpu_warmup/null explícito; no forzar HEALTHY ni restaurar un baseline antiguo.
La pausa E sí produjo warmup porque dejó de adquirir durante más de180s.

## Aceptación, abortos y riesgos

Aceptar F sólo con evidencia de intentos reales fallidos/bounded, baseline
adquiriendo, last_seen sin renovación y transición UNKNOWN/OFFLINE; core/NAS
permanecen frescos y avanzan independientemente. Tras restaurar: nuevo collected_at,
HTTPS normal aceptado, sin payloads atrasados/replay inesperado, salud conforme
métricas, sin duplicación y hashes/permisos/unidades intactos. Registrar si el
watchdog llegó a disparar o se canceló tras restauración anticipada.

Abortar/restaurar si falla el observador, otro nodo deja de estar fresco,
9444 se vuelve accesible, hay drift de config/CA/token/unidades, tiempo no
confiable, errores fuera de límites o recuperación incompleta. No arreglar la
red ni el core para continuar. Cada ejecución usa un marcador consumido, sin
borrarlo o reintentar una escritura incierta.

Riesgos previstos: error genérico visible en el collector, datos notebook
UNKNOWN/OFFLINE, agregado del sitio UNKNOWN, una escritura atómica de config
y posible intento aún en curso al restaurar. El token sigue sujeto a TLS
verificado; no enviarlo a un endpoint inesperadamente activo. El helper no pisa
un cambio externo de configuración: ante drift requiere revisión del operador.
El límite depende del gestor/FS sanos; no se presenta como garantía de tiempo
real ante fallos del host. No hay impacto administrativo previsto en SSH,
navegador o9443 normal; su continuidad se comprobará durante el ensayo.
