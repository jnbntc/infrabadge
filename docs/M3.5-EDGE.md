# M3.5 — edge HTTPS y despliegue de laboratorio

El diseño siguiente conserva la preparación original. El despliegue autorizado
posterior usa un edge rootless en la LAN cableada de Fedora hacia el Core por
HTTPS privado. Ver [resultados físicos y límites](M3.5-PHYSICAL-RESULTS.md).

El servicio sigue siendo `python -m infrabadge_gateway.distributed.cli edge`.
Reutiliza dependencias fijadas, imagen ARM64/x86_64 y plantilla Quadlet de M3.2;
no requiere SQLite en el edge. El Core sí debe ejecutar el código M3.5 antes de
habilitar el dispositivo v2: el despliegue M3.2 anterior no sirve la ruta nueva.
La base conserva esquema2, configuración/backup/rollback deben verificarse en
la actualización autorizada. La preparación original no actualizó procesos;
el despliegue posterior está documentado en el informe enlazado.

## Entradas privadas necesarias

- Origen fijo Core HTTPS9443 accesible desde el host edge; CA explícita y SAN
  coincidente, fechas válidas. El badge no usa Tailscale.
- Identidad edge independiente, limitada a los dispositivos aprobados. El token
  de dispositivo se valida en Core y se transporta únicamente en ambos saltos TLS.
  Nunca usar credencial reader/collector como edge o device.
- Dispositivo Core con `presentation_v2=true` y scope de hasta tres sitios/seis
  nodos habilitados. `deploy/m35/core-device.example.json` muestra sólo campos
  adicionales de ejemplo: NO reemplaza la identidad ni contiene hashes válidos.
- Configuración edge basada en `deploy/m35/edge.example.json`, cuyo dominio
  `.test` es sintético; no es un nombre DNS de producción.
- Leaf/key del edge, CA pública para badge, nombre DNS LAN estable con SAN exacto;
  CA Core distinta admitida en edge. Archivos privados fuera de Git, directorio
  0700 y claves/tokens0600. Ninguna clave CA va al ESP32.

Un leaf renovado con la misma CA/SAN puede conservar la confianza del badge;
comprobar cadena/fechas. Cambio de CA/nombre/URL/token necesita una provisión
USB autorizada. No se generó PKI real ni se presupone que la CA actual sirve.
Base URL y CA deben caber en los límites de configuración M2 existentes.

## Comando de ejecución futuro, NO instalación

Con el venv fijado y rutas privadas ya preparadas, el proceso admite:

```sh
python -m infrabadge_gateway.distributed.cli edge \
  --config /ruta/privada/edge.json \
  --cert /ruta/privada/edge-leaf.pem --key /ruta/privada/edge.key \
  --bind IP_LAN_EXACTA_APROBADA --port 8443
```

No ejecutarlo todavía. El ejemplo no contiene tokens en argv; éstos se leen
sólo del archivo privado. No usar wildcard, proxies de ambiente, redirects ni
CA global modificada. Para Podman, la plantilla inerte M3.2 publica sólo una IP
LAN exacta y monta credenciales read-only. No instalarla sin revisión de sitio.

## Preflight y despliegue con autorización posterior

1. Elegir host permanente y LAN compartida con el ESP32; preferir el Core si su
   LAN corresponde. Comprobar DNS, SAN, interfaz/origen LAN y camino de retorno;
   la notebook móvil y el viejo gateway localhost no son dependencias.
2. Inspeccionar listeners/firewall/VPN sin cambios; identificar si se necesita
   una regla de retorno específica. No aplicar reglas de ensayos M2 anteriores.
3. Aprobar separadamente actualización Core, identidad/scopes, PKI/DNS, servicio
   edge y exposición firewall mínima. No abrir9443 a la LAN/Internet para el badge.
4. Preparar restauración independiente de exposición/servicio antes de habilitar
   el listener. El rollback de imagen/config Core no elimina ni restaura SQLite
   automáticamente. Nunca usar un backup antiguo para descartar muestras nuevas.
5. Prueba externa con CA explícita:200/304 sin ampliar expires_at,401/403 y fallo
   cerrado ante CA/SAN/fechas, pérdida del Core y posterior recuperación.
6. Sólo después autorizar la aplicación M3.5 y su provisión privada/UTC. La prueba
   software no demuestra DNS/routing real ni TLS del ESP32.

El edge mantiene budgets global y por dispositivo, tamaño4096B, encabezados8KiB,
body GET vacío, espera I/O4s y plazo global6s, sin caché persistente. Para v2
revalida modelo completo, identidad, ETag y vencimiento en200/304; errores son
401/403/429/503 saneados sin cuerpo upstream. No renueva una muestra caducada.

En la preparación original, las plantillas eran inertes y la conectividad, PKI
y permisos reales estaban pendientes. No se modificó el host en aquella etapa.
La evidencia posterior y la guardia limitada del edge están separadas en
[M3.5-PHYSICAL-RESULTS](M3.5-PHYSICAL-RESULTS.md); no implican cambios de DNS,
VPN, Grants ni firewall del Core.
