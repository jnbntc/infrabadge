# M3.2 — incidencia transitoria del collector local

## Dictamen

**Recuperación confirmada; causa indeterminada.** Evidencia compatible con un
rearmado temprano del timer que violaría el mínimo entre muestras nuevas. El
collector sólo registró `collection_or_submission_failed`: **HTTP429 no fue
capturado**, y no se declara un bug de aplicación corregido ni causa resuelta.
No se reprodujo el fallo modificando listeners, timers, credenciales o hosts.

## Hipótesis y límites

- Política central: min_interval15s; el segundo envío cae antes de ese mínimo.
  Las fechas registradas son coherentes con un rechazo por frecuencia.
- Timer con OnActiveSec5s y OnUnitInactiveSec30s. Reload/activación durante la
  transición coincide con ese segundo disparo; no se atribuye un bug de systemd
  ni se prueba un mecanismo de carrera sólo a partir de esa secuencia.
- Gateway, TLS/listeners e inventario estaban cambiando de forma autorizada.
  Un fallo de transporte/config no puede excluirse con el error genérico.
- Los hashes finales de las dos unidades locales y de la aplicación quedaron
  intactos. Las copias de credencial siguen el mismo mecanismo temporal.
  Eso descarta drift persistente observado, no acredita el contenido de cada
  entrega de credenciales en el instante fallido.
- Hubo éxito antes/después, ningún fallo adicional en la ventana final revisada
  y el restart posterior no lo repitió. No demuestra estabilidad prolongada.

La incompatibilidad root/0440 de LoadCredential ocurrió en la activación inicial
anterior del piloto: es **otro incidente**, corregido mediante copia propia0600.
Los errores de los helpers (medición de un proceso terminado, comparación de
timedated y una variable omitida) tampoco se atribuyen al collector.

## Regresión y decisión

`test_restart_and_early_timer_delivery_rejects_without_changing_watermark` usa
fixture sintético, persistencia real temporal y API local: muestra aceptada,
restart lógico, envío nuevo a+9s con mínimo15s→429 sin mover watermark/histórico,
luego+40s→202 y salud fresca. Es **SOFTWARE VALIDATED de la política**, no prueba
del HTTP histórico ni una reproducción del rearmado de systemd en la Pi.

No hay corrección funcional demostrada que aplicar a la app. Se conserva el
rechazo por frecuencia y no se añaden retries ilimitados, se borra baseline o
modifica el reloj. Cualquier instrumentación nueva necesitará alcance separado.

## Prevención operativa propuesta

Antes de un mantenimiento futuro autorizado: poner inactivo el oneshot antes de
daemon-reload/rearmado y coordinar timer/ejecuciones manuales con el mínimo de
ingestión. Tras una muestra manual esperar al menos16s en la política local15s;
para la política remota30s, al menos31s. Si se desconoce el último envío, observar
una ventana completa de la política en lugar de suponer que el timer quedó
alineado. No hacer disparos manuales simultáneos con el timer.

Verificar después received/last_seen avanzando, al menos dos ciclos con delta
CPU válido, Result=success/ExecMainStatus0 y ausencia de nuevos fallos. Un
oneshot inactive/dead puede ser normal; no medir recuperación sólo con ActiveState.
No borrar journal/reset-failed para simular un historial limpio. No se ejecutó
ese mantenimiento durante esta revisión.

Para confirmar causa en un próximo evento se necesitaría evidencia saneada que
distinga fase de adquisición, transporte y código HTTP sin revelar credenciales.
Hasta entonces, este diagnóstico permanece abierto con hipótesis respaldada.
