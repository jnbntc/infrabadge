# M3.2 — ARM64, operación nativa y rollback

Existe un piloto nativo ARM64/Python3.13.5/systemd documentado en
[PHYSICAL-VALIDATION](M3.2-PHYSICAL-VALIDATION.md). Las plantillas públicas no son
las configuraciones privadas instaladas: no contienen inventario, IPs, DNS o
credenciales reales. Esta consolidación no instala ni actualiza nada. No ejecutar
comandos operativos sin aprobación específica del sitio.

## Artefactos

- `deploy/m32/Containerfile`: Python3.12 por digest, lock con hashes, sin paquetes
  del host, UID10001, mismos módulos en ARM64/x86_64.
- Dos Quadlets `.container.in`: core con IP Tailscale explícita:9443 y directorio
  SQLite RW local, edge con IP LAN explícita:8443 y config RO. No wildcard host,
  host network, privilegios, Docker socket o root service.
- `core.example.json`: vacío/deshabilitado; no arrancar como inventario real.
- `grants.proposal.json`: propuesta por revisar, no tailnet policy desplegable.
- Mismo collector zip stdlib, servicio/timer usuario M3; parametrizar node_id,
  montaje Linux, CA/URL/token privado. No ejecutar collector en namespace de
  contenedor como si sus proc/sys/mounts fueran los del host.

## Native systemd: adaptaciones reales publicadas como candidatos

`deploy/m32/native/` conserva el adaptador de dos sockets ya empleado, con la IP
privada retirada y dos `--listener` obligatorios. Son un proceso/worker/Core/Store,
no dos apps SQLite. La unidad socket usa Accept=no, dos ListenStream exactos y
FreeBind; el adaptador valida LISTEN_PID/FDS, IPv4 TCP/listening y direcciones.
No inicia un bind por su cuenta. Estas unidades reproducen la fase ampliada:
para un piloto exclusivamente loopback usar el CLI existente con `--bind 127.0.0.1`, no abrir overlay para satisfacer la plantilla
ni iniciar dos procesos. Su futura activación requiere aprobación propia. [Socket activation](https://www.freedesktop.org/software/systemd/man/latest/systemd.socket.html).

Cuatro `.in` reproducen las unidades nativas con campos privados pendientes:
core.service/core.socket y collector.service/collector.timer. Renderizar fuera
del repositorio con release/adapter absolutos, cuentas/grupos aprobados, paths
privados de config/estado/credencial y dirección overlay exacta. No ejecutar una
plantilla sin completar ni copiarla sobre unidades existentes. Mantener el mismo
nombre entre COLLECTOR_UNIT, RuntimeDirectory y timer; escoger la cadencia de
la política privada (piloto local30s, remoto60s; no son nuevos defaults).

`requirements-runtime.lock` es el subconjunto de17 paquetes del lock completo,
con versiones/hashes idénticos, usado en el piloto. En un despliegue nuevo aprobado:
venv aislado, instalación con --require-hashes, pip check y release no escribible
por cuentas de servicio. Puede prepararse wheelhouse y transferirse offline sin
secretos. No añadir la clave CA privada al bundle ni usar pip global. CI valida
Python3.13.5 ARM64/x86_64; la imagen alternativa conserva su Python3.12 fijado.

Config y key deben ser0600 del UID efectivo; DB/baseline en directorios0700,
sin symlinks o shares. Administrador y cuenta runtime son roles distintos: la
CLI core rechaza UID0. Para LoadCredential, systemd puede entregar root/0440:
ExecStartPre ejecutado como collector hace install -m0600 hacia RuntimeDirectory
propio0700, y la CLI usa esa copia. RuntimeDirectoryPreserve=no la retira al
terminar cada oneshot. No relajar private_bytes para aceptar la credencial original.

MemoryMax256/64MiB declarado sólo actúa si el controlador memory está habilitado.
En el central no lo está; LimitAS512/128MiB observado es espacio virtual por
proceso, **no cap equivalente de RAM**. En remoto se observó memory.max64MiB.
No se habilita memory ni reinicia el host. No hay CPUQuota en estas unidades:
no inferir una cuota por ver el controlador cpu. CPU/pids, RSS y cgroup son
magnitudes distintas. La limitación operativa permanece aceptada y visible.

Validar sin instalar ni leer secretos:

```sh
python tools/m32/check_native.py --verify-systemd
```

Usa paths temporales y TEST-NET únicamente para sintaxis, comprueba el lock y
no ejecuta systemctl start/daemon-reload. No prueba sandbox/arranque del host.
Antes de una instalación nueva: cotejar artefactos y renderer, validar permisos,
TLS/UTC, FS/montaje y firewall existente; pedir autorización para cuentas,
directorios, unidades y servicios. No hay instalador automático en esta tarea.

## CI y reproducibilidad

BuildKit fijado por digest y base Python fijada. CI nativa `ubuntu-24.04` y
`ubuntu-24.04-arm`: dos builds limpios sin cache, SOURCE_DATE_EPOCH0, timestamps
OCI normalizados, SBOM/provenance no variables; comparación de manifiesto
content-addressed. No comparar bytes de tar de transporte ni imágenes entre
arquitecturas. Smoke offline no-root en ambas arquitecturas: ingestión sintética,
contrato M2, migración, backup y restore histórico. No publica imágenes en registry.
Los resultados efectivos se registran por SHA del PR, no se presuponen.

La ruta A de contenedores requiere SO64bit, Podman rootless, systemd usuario y
almacenamiento local con locking/durabilidad adecuados. Su build ARM64 no valida
por sí solo una Raspberry Pi física ni prueba esa instalación de contenedores.
La ruta B nativa sí tiene evidencia Linux del piloto, con capturas acotadas de
CPU/RSS; no equivale a estabilidad prolongada, endurance de SD o autonomía.
Ver [evidencia y límites](M3.2-PHYSICAL-VALIDATION.md).

## Plan progresivo para una instalación nueva

1. Aprobar inventario privado y permiso organizacional; habilitar sólo nodos
   permitidos. Verificar SO/arquitectura/rootless/storage/hora mediante acceso
   autorizado aparte. No habilitar linger automáticamente.
2. Revisar transporte privado real/tailnets y Grants completos. Aprobar sólo
   telemetría TCP9443; ningún puerto administrativo o enrutamiento de subredes.
3. Preparar CA/leafs/SAN/DNS reales y tokens únicos, archivos0600/directorios0700.
   Custodiar clave de CA fuera de mounts. Nunca usar credenciales en argv/logs.
4. Elegir camino: A imagen rootless con ID/digest inmutable; B venv nativo
   y unidades descritas arriba, sin añadir un runtime de contenedores.
   Instalar core inicialmente accesible sólo por loopback, con DB nueva separada
   de todo estado M3. Prueba local autenticada, backup y recuperación; luego bind
   a IP Tailscale exacta tras preflight aprobado. Una sola instancia/worker.
5. Migrar **un collector**: backup de sus archivos, crear credencial específica,
   mapear nodo/sitio/política, cambiar URL/CA privadas y autorizar timer de usuario.
   Verificar202, idempotencia, stale/OFFLINE y recuperación. Expandir de a uno;
   trabajo permanece deshabilitado hasta permiso organizacional.
6. Preparar edge local de cada sitio con origen central fijo y credencial edge
   distinta; preflight LAN equivalente a M3.1, incluyendo VPN/trusted/otras zonas.
   El bind de IP no garantiza interfaz. Ninguna plantilla modifica firewall.
7. Probar ambos edges contra la misma fuente y comprobar ETag/TTL/roles/aislamiento.
   Después solicitar ensayo del ESP32; no flasheo previsto, posible provisión
   física de Wi-Fi/URL/CA/UTC separada. Confirmar pantalla con operador.

Mantenimiento del piloto: consultar
[M3.2-COLLECTOR-INCIDENT](M3.2-COLLECTOR-INCIDENT.md), coordinar rearmado con
min_interval y no solapar ejecuciones manuales/timer. El piloto de dos nodos ya
está validado; los pasos anteriores describen nuevas instalaciones, no un permiso
para repetir escrituras o convertir deuda de DR en bloqueo retroactivo.

La notebook móvil puede suspenderse: timer no acumula backlog ni despierta host;
intervalo normal60s y CPU delta reinicia tras gap. `delivery_attempts:2` es opt-in,
dentro del timeout total; TLS/certificados/HTTP rechazado no se reintentan. No hay
spool ilimitado de muestras antiguas. No cambiar servicios M3 reales ahora.

## Comandos preparados de persistencia

Desde entorno Python con lock aislado, PYTHONPATH apuntando a `gateway/`. Son
operaciones sobre base privada elegida por el operador, no comandos ya ejecutados
en una base operativa:

```sh
python -m infrabadge_gateway.distributed.cli check --database /RUTA/PRIVADA/core.db
python -m infrabadge_gateway.distributed.cli backup --database /RUTA/PRIVADA/core.db --output /RUTA/PRIVADA/backup-nuevo.db
python -m infrabadge_gateway.distributed.cli migrate --database /RUTA/PRIVADA/core.db
python -m infrabadge_gateway.distributed.cli restore --database /RUTA/PRIVADA/backup-nuevo.db --output /RUTA/PRIVADA/restaurada-nueva.db
```

Validar backup antes de migrar. `migrate` necesita exclusión del writer; no usar
con servicio activo. Restore crea otra base, no cambia unidad/bind ni arranca
servicios. Política de backups propuesta: mantener al menos dos puntos válidos,
retención/cifrado/acceso aprobados por el operador, nunca rotación sobre backups
M2/fábrica o historial de otros proyectos.

## Rollback

Con socket activation, parar únicamente core.service no retira el listener:
PID1 puede conservarlo y reactivar la app. Para detener el piloto bajo aprobación,
parar primero timers/oneshots de los collectors afectados y detener **socket y
service** del core; confirmar que no queda9443. Para retirar sólo la ampliación
remota, preservar el collector local y volver a su listener loopback mediante
el plan privado validado, sin restaurar automáticamente una DB antigua.

La reversión del NTP remoto es separada y no necesaria para retirar su collector.
La parada/reactivación remota se ejercitó; rollback completo del central sólo
validado por copias/hashes/sintaxis y nft -c, no ejecutado end-to-end. Backups
externos, segunda tarjeta y DR siguen diferidos por el operador. No se ensayan
ni se convierten en nuevos bloqueos de la consolidación.


Antes de activar: registrar hashes de config/unidades originales e ID de imagen,
respaldar DB mediante API y conservar archivos M3 sin reemplazarlos. Para rollback
del piloto, detener sólo core/edge nuevos y restaurar configs/URL/CA/token/timer
del collector afectado desde copias revisadas. Gateway M3 localhost conserva su
base de funcionamiento en RAM y su contrato; el firmware no se restaura.

Si se necesita volver a una DB M3.2 anterior, restore a un destino nuevo y validar
schema/integridad, luego cambiar la unidad bajo autorización. Históricos quedan
no frescos y watermarks posteriores al backup se perdieron; coordinar clientes.
Nunca abrir schema nuevo con binario antiguo ni ejecutar downgrade SQL automático.
Retirar sólo reglas/Grants/unidades que el piloto haya añadido, con selectores
exactos; sin flush global, cambios VPN o borrado de datos privados.

Autorizaciones para cambios futuros (no heredadas de instalar el piloto):
SSH/inspección nueva de otros equipos; servicios/volúmenes y cambios
de config reales; política de tailnet/red/DNS; exportación laboral; credenciales y
TLS; provisión/ensayo ESP32; merge. Mediciones eléctricas siguen pospuestas.
