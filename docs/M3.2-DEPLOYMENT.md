## Artefactos

- `deploy/m32/Containerfile`: Python3.12 por digest, lock con hashes, sin paquetes
  del host, UID10001, mismos módulos en ARM64/x86_64.
- Dos Quadlets `.container.in`: core con IP Tailscale explícita:9443 y directorio
  SQLite RW local, edge con IP LAN explícita:8443 y config RO. No wildcard host,
  host network, privilegios, Docker socket o root service.
- `core.example.json`: vacío/deshabilitado; no arrancar como inventario real.
- `grants.proposal.json`: propuesta por revisar, no tailnet policy desplegable.
- Mismo collector zip stdlib, servicio/timer usuario M3; parametrizar node_id,
  montaje Linux, CA/URL/token privado. No ejecutar collector en namespace de
  contenedor como si sus proc/sys/mounts fueran los del host.

## CI y reproducibilidad

BuildKit fijado por digest y base Python fijada. CI nativa `ubuntu-24.04` y
`ubuntu-24.04-arm`: dos builds limpios sin cache, SOURCE_DATE_EPOCH0, timestamps
OCI normalizados, SBOM/provenance no variables; comparación de manifiesto
content-addressed. No comparar bytes de tar de transporte ni imágenes entre
arquitecturas. Smoke offline no-root en ambas arquitecturas: ingestión sintética,
contrato M2, migración, backup y restore histórico. No publica imágenes en registry.
Los resultados efectivos se registran por SHA del PR, no se presuponen.

El contenedor de ARM64 no prueba Raspberry Pi físico: el host futuro debe tener
SO64bit compatible, Podman rootless, systemd usuario y almacenamiento local con
semántica de locking/durabilidad adecuadas. No se verificaron esos requisitos
por SSH. CPU/memoria/SD/autonomía no están caracterizadas.

   permitidos. Verificar SO/arquitectura/rootless/storage/hora mediante acceso
   autorizado aparte. No habilitar linger automáticamente.
2. Revisar transporte privado real/tailnets y Grants completos. Aprobar sólo
   telemetría TCP9443; ningún puerto administrativo o enrutamiento de subredes.
3. Preparar CA/leafs/SAN/DNS reales y tokens únicos, archivos0600/directorios0700.
   Custodiar clave de CA fuera de mounts. Nunca usar credenciales en argv/logs.
4. Construir la imagen de la revisión aprobada y registrar ID/digest inmutable.
   Instalar core inicialmente accesible sólo por loopback, con DB nueva separada
   de todo estado M3. Prueba local autenticada, backup y recuperación; luego bind
   a IP Tailscale exacta tras preflight aprobado. Una sola instancia/worker.
5. Migrar **un collector**: backup de sus archivos, crear credencial específica,
   mapear nodo/sitio/política, cambiar URL/CA privadas y autorizar timer de usuario.
   Verificar202, idempotencia, stale/OFFLINE y recuperación. Expandir de a uno;

7. Probar ambos edges contra la misma fuente y comprobar ETag/TTL/roles/aislamiento.

## Comandos preparados de persistencia

Desde entorno Python con lock aislado, PYTHONPATH apuntando a `gateway/`. Son
operaciones sobre base privada elegida por el operador, no comandos ya ejecutados
en una base operativa:

```sh
python -m infrabadge_gateway.distributed.cli check --database /RUTA/PRIVADA/core.db
python -m infrabadge_gateway.distributed.cli backup --database /RUTA/PRIVADA/core.db --output /RUTA/PRIVADA/backup-nuevo.db
python -m infrabadge_gateway.distributed.cli migrate --database /RUTA/PRIVADA/core.db
python -m infrabadge_gateway.distributed.cli restore --database /RUTA/PRIVADA/backup-nuevo.db --output /RUTA/PRIVADA/restaurada-nueva.db
```

Validar backup antes de migrar. `migrate` necesita exclusión del writer; no usar
con servicio activo. Restore crea otra base, no cambia unidad/bind ni arranca
servicios. Política de backups propuesta: mantener al menos dos puntos válidos,
retención/cifrado/acceso aprobados por el operador, nunca rotación sobre backups
M2/fábrica o historial de otros proyectos.

## Rollback

Antes de activar: registrar hashes de config/unidades originales e ID de imagen,
respaldar DB mediante API y conservar archivos M3 sin reemplazarlos. Para rollback
del piloto, detener sólo core/edge nuevos y restaurar configs/URL/CA/token/timer
del collector afectado desde copias revisadas. Gateway M3 localhost conserva su
base de funcionamiento en RAM y su contrato; el firmware no se restaura.

Si se necesita volver a una DB M3.2 anterior, restore a un destino nuevo y validar
schema/integridad, luego cambiar la unidad bajo autorización. Históricos quedan
no frescos y watermarks posteriores al backup se perdieron; coordinar clientes.
Nunca abrir schema nuevo con binario antiguo ni ejecutar downgrade SQL automático.
Retirar sólo reglas/Grants/unidades que el piloto haya añadido, con selectores
exactos; sin flush global, cambios VPN o borrado de datos privados.
