# M3.1 — preparación e instalación controlada

**No instalado.** Este procedimiento requiere autorización específica antes de
copiar unidades activas, cambiar firewall/rutas/DNS o reiniciar servicios. La
autorización de merge M3 no autoriza despliegue LAN. No requiere flasheo.

## Preparación reproducible sin activar servicios

Desde este checkout, ejecutar las pruebas con el entorno Python del gateway
aislado y dependencias de `gateway/requirements.lock`; Ruff usa
`tools/m3/style.lock`. No instalar paquetes en el Python de Fedora/ESP-IDF.

```sh
python3 tools/m31/check_candidate.py --quadlet
```

Usa política ficticia, genera un bundle temporal, comprueba ZIP y sintaxis de
unidades y hace dry-run del generador Podman ya instalado. No hace daemon-reload,
arranque, firewall, DNS ni sockets LAN. Si no hay Podman, omitir `--quadlet` deja
la comprobación de unidades; la prueba del generador queda pendiente explícita.

La futura imagen se construye desde `deploy/m31/Containerfile` con el mismo lock
M3 y base fijada. Su ID local real `sha256:...` debe copiarse a la política después
de construirla y probarla: el ID ficticio del ejemplo no es desplegable. El
preparador no construye ni descarga imágenes. El límite candidato es 256 MiB,
64 procesos y una CPU; verificar compatibilidad rootless/cgroup v2 y consumo real.

Crear fuera de Git una política JSON privada0600 en carpeta0700. El ejemplo
`deploy/m31/policy.example.json` sólo explica campos: **no es inventario ni
configuración autorizada**. Completar con datos verificados localmente, sin
compartir SSID/UUID/direcciones por Git o logs públicos. El hash del SSID no es
anonimización resistente a diccionario. `firewall_sha256` corresponde al texto
exacto de `firewall-cmd --zone=ZONA --list-all`, quitando sólo newlines finales,
después de revisar reglas; no copiar ciegamente un hash para que pase el guard.

```sh
python3 tools/m31/prepare.py --policy /ruta/privada/policy.json --output /ruta/privada/bundle-nuevo
```

Produce política, tres unidades, guard ZIP determinista y plan privado. No
sobrescribe directorios existentes ni escribe dentro del repositorio. El plan
incluye selectores propuestos de firewall y add/delete de ruta; son datos para
revisar, **no comandos ejecutados**. No usar `eval` sobre el JSON.

## Decisiones pendientes y red

La inspección de sólo lectura de2026-10-19 detectó retorno TCP8443 desviado por
VPN y un permiso amplio del puerto en la zona Wi-Fi. Es evidencia histórica,
no garantía del estado actual. Revalidar antes de autorizar. Este candidato
deliberadamente no funcionará hasta resolver ambas condiciones.

Preparar un plan con diferencias exactas y rollback, revisado por el operador:

1. Perfil Wi-Fi autorizado y zona dedicada/revisada. Evitar alterar zonas o
   permisos de otras redes. Revisar servicios, rich rules, políticas globales,
   forwarding, router y cualquier port-forward WAN. No publicar hacia Internet.
2. Autorizar sólo IPv4 origen-subred LAN a la IP seleccionada/32 TCP8443,
   ligada al perfil/interfaz autorizado. Quitar un permiso amplio existente sólo
   si se confirma que no lo usan otros servicios. No abrir puertos globalmente.
3. Si el retorno sigue desviado, evaluar regla **del perfil Wi-Fi** con prioridad
   libre5100, origen gateway/32, destino subred, ipproto TCP, sport8443, tabla main.
   Comprobar conflictos y soporte instalado de NetworkManager. No cambiar VPN,
   tabla por defecto ni todas las conexiones. Preferir primero ensayo temporal
   acotado con limpieza independiente, luego persistencia sólo si se autoriza.
4. Resolver hostname SAN a IP accesible desde la Wi-Fi, con Avahi por interfaz
   o DNS local controlado. El resolver del host no sustituye al cliente LAN.
   No cambiar DNS global/router/reserva DHCP sin autorización separada.

La política fija una IPv4; cambio DHCP exige nuevo plan y reinicio controlado de
la publicación. Cambiar SSID/perfil o pasar a red corporativa no debe autorizarse
por parecido del nombre. IPv6 LAN no está publicado en este candidato.

## Certificados y credenciales

La carpeta dedicada `~/.config/infrabadge/m31` debe contener `gateway.json`,
`policy.json`, `ca.pem`, `server.pem`, `server.key`, todos privados. No montarla
junto a backups o claves de CA. `gateway.json` conserva la configuración M3 real,
roles separados y `enable_faults=false`. La entrada LAN sólo acepta dispositivos
reales. El certificado debe validar **localhost y hostname LAN** y estar vigente;
el servidor comprueba CA/SAN/fechas/clave antes de arrancar. Hora UTC del host confiable.

El certificado M3 inspeccionado vencía2026-11-18T15:22:20Z. El generador de ese
laboratorio descartó la clave de firma de su CA: **no existe renovación transparente
del leaf con esa CA disponible**. Elegir antes del despliegue entre conservar
temporalmente el certificado aún vigente o emitir CA nueva con custodia de su
clave fuera del contenedor. CA nueva requiere provisión física USB explícitamente
autorizada en la placa; no cambio de firmware. Nunca copiar una CA nueva sólo al
gateway y declarar que el ESP32 seguirá confiando en ella. Ver rotación en SECURITY.

## Aplicación futura, sólo después de aprobar el plan

Guardar copias0700/0600 del Quadlet M3 anterior, ID de imagen, configuración,
certificados y estado de unidades; no reemplazar sus backups. Mantener collector
host y sus credenciales originales. Confirmar que no existe otra instancia.

Instalar guard ZIP en `~/.local/share/infrabadge-lan-guard/`, las unidades guard
en `~/.config/systemd/user/`, y reemplazar el único Quadlet
`~/.config/containers/systemd/infrabadge-gateway.container` por el revisado. Copiar
sólo archivos enumerados, con permisos restrictivos; nunca un árbol privado entero.
Revisar imagen, publicaciones exactas, mounts RO/RW y SELinux `:Z` sin desactivar
SELinux. Luego daemon-reload, activar timer guard y arrancar/reiniciar el único
`infrabadge-gateway.service`. El [Install] del Quadlet gestiona arranque en el
manager de usuario; no habilitar una unidad generada como si fuera archivo normal.
No habilitar linger ni instalar servicios de sistema.

Antes de dejarlo operativo verificar loopback collector→200/304, cliente TLS LAN
autorizado, rechazo desde otra interfaz, firewall real, pérdida de red, reinicio
de gateway, caducidad y recuperación. Ensayar suspend/logout sólo con autorización.
La placa existente puede necesitar UTC renovado tras un reset frío: intervención
separada, no reusar planes USB consumidos. Ninguna etapa ejecutada aquí accede a USB.

## Operación y rollback

Consultas de sólo lectura después de instalar:

```sh
systemctl --user status infrabadge-gateway.service infrabadge-lan-guard.timer infrabadge-collector.timer
journalctl --user -u infrabadge-lan-guard.service --since '10 minutes ago'
python3 tools/m31/status.py --policy "$HOME/.config/infrabadge/m31/policy.json" --lease "$XDG_RUNTIME_DIR/infrabadge-lan-guard/lease.json" --telemetry "$XDG_RUNTIME_DIR/infrabadge-lan-telemetry/state.json"
```

No imprimir configs/tokens en diagnósticos. Los logs del contenedor están
deshabilitados; guard sólo publica approved/unavailable. El estado privado no
demuestra disponibilidad: comprobar servicio y TLS por separado. Tras suspensión,
observar permiso nuevo y muestra fresca; contadores de consulta no prueban timer.

Rollback autorizado: detener gateway candidato, restaurar exactamente Quadlet,
imagen y archivos M3 guardados; daemon-reload y arrancar el único gateway original
localhost. Detener/deshabilitar timer guard y retirar sólo sus archivos dedicados.
Retirar únicamente regla/ruta del plan si fueron añadidas; restaurar permisos
previos sólo según el diff aprobado, sin flush de reglas ni cambios VPN/DNS
globales. Confirmar ausencia listener LAN, collector activo y muestra local fresca.
No restaurar flash/NVS/fábrica. Si se rotó CA/token en placa, el rollback debe
conservar confianza/credencial compatibles, o necesita otra provisión autorizada.
