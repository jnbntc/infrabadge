## Decisión: reutilizar la instalación M3

El zipapp instalado coincide, módulo por módulo y byte por byte, con el collector
de M3 (`df11e98`). Una adquisición sin envío desde ese archivo produjo métricas
que acepta el modelo Pydantic de M3.2. Su configuración propuesta también pasa
el validador instalado. No hace falta actualizar código, Python, dependencias,
servicio ni timer para cambiar el destino.

Flujo aplicado en D: collector de usuario existente → HTTPS verificado por Tailscale
→ core M3.2 → SQLite. El gateway M3 local queda conservado; no participa en el
nuevo envío ni se configura failover hacia él. No hay un segundo collector.

| Elemento | Decisión aplicada en D |
| --- | --- |
| Identidad | `fedora-notebook`, display `NOTEBOOK`, tipo `mobile` |
| Sitio | `home`, asignado en el servidor; no cambia al cambiar de Wi-Fi |
| Autenticación | Token nuevo exclusivo, sólo rol collector de ese nodo |
| Transporte | Nombre del core ya incluido en SAN, CA central existente, TCP 9443 |
| Adquisición | Host real, sin root ni namespace de contenedor; montaje actual conservado |
| Cadencia | Unidad existente: 60 s tras finalizar, coalescing 5 s, arranque inicial 30 s |
| Límites | Deadline HTTP total 10 s, TimeoutStartSec 20 s, un intento por ejecución |
| Estado CPU | Archivo nuevo para M3.3; baseline M3 conservado para rollback |
| Salud | TTL 180 s, max_gap 180 s, mínimo 30 s, OFFLINE a 360 s |
| Temperatura | Sólo sensor identificado; sin umbrales nuevos |

La política conserva CPU 85/95 % durante tres muestras, memoria/disco disponibles
15/5 %, recuperación de dos muestras e histéresis existente. Los dos nodos
anteriores conservan sus políticas. Un nodo recién dado de alta, sin muestra,
es UNKNOWN; HEALTHY requiere datos frescos y métricas que lo justifiquen.

## Contrato y movilidad

M3 y M3.2 comparten schema_version 1, POST
`/api/v1/collectors/{node_id}/metrics` y ACK 202 `{"accepted":true}`.
El payload no transporta site_id ni una secuencia nueva: el servidor usa
identidad, collected_at y digest. Duplicado idéntico no renueva frescura; replay
se rechaza. Ningún cambio de red mueve el nodo entre sitios.

No hay daemon, cola persistente, spool de muestras ni reenvío de datos antiguos
desde el timer. Cada ejecución adquiere una muestra nueva. El baseline se guarda
antes de enviar: si falla la red pero la notebook sigue despierta, puede seguir
habiendo deltas locales válidos. Una suspensión larga invalida el delta por gap;
no debe confundirse ese caso con una pérdida de transporte.

No se instalan hooks de suspensión, se habilita linger ni se cambia el reloj.
Los aspectos que aún necesitan prueba real están en
[MOBILITY-VALIDATION](M3.3-MOBILITY-VALIDATION.md).

## Seguridad y disponibilidad

La autorización de aplicación, la regla exacta del firewall del core y la
política Tailscale son controles distintos. No se abre ningún listener en Fedora,
se crea Funnel, exit node, subnet router o ruta entre casa y trabajo.

La política del control plane Tailscale no fue obtenida en este preflight;
no se afirma aislamiento completo de la tailnet. Antes de cambiar Grants se
necesita otra revisión/autorización. El firewall de D añadió una única aceptación
exacta notebook/32→core/32
TCP9443 por tailscale0, antes del descarte y conservando la regla remota anterior.
La comprobación de los Grants completos sigue pendiente; la conexión exitosa
no acredita exclusividad de toda la tailnet.

El inventario se carga al iniciar Core. Añadir el nodo exigió un reinicio corto
del único proceso core, conservando socket, DB y timers existentes. Las muestras
persistidas se consideran históricas/UNKNOWN hasta nuevas entregas. Se verificó
la recuperación de los tres nodos con datos nuevos, sin prometer HEALTHY continuo
durante el mantenimiento.
