# M3.6 — roaming acotado y suspensión nocturna

PR9 está integrado en main; el firmware M3.6 está instalado y validado durante
el día exclusivamente en CASA. Noche sigue deshabilitada; TRABAJO no tiene binding.
Estado operativo y evidencia acotada en [CASA-STABLE](CASA-STABLE.md).

## Código y límites de selección

Nuevo perfil `roaming`: aplicación M3.5 con extensión compilada únicamente
con `CONFIG_IB_M36_ROAMING`, componente `mobile_policy`. Dos rutas como máximo,
una por red distinta; sin escaneo/discovery de URLs, portal cautivo, DNS dinámico,
Tailscale en ESP32 ni fallback inseguro. Si dos sitios comparten SSID, se rechaza
la configuración: esta primera versión no puede distinguirlos de forma segura.

La ruta lógica (`site_id`, índice de binding) se separa de los archivos privados
SSID/clave, URL fija HTTPS, CA y token. El SSID sólo ayuda a elegir asociación;
la identidad del edge se verifica mediante CA, SAN/nombre, fechas y autenticación
Core. Primero intenta la última ruta exitosa y luego la otra **sólo si falla
Wi-Fi**. Fallos TLS/HTTP/auth terminan la consulta, no prueban credenciales en
otra URL de esa red. No se aprende ningún endpoint desde respuestas no fiables.
Cada intento Wi-Fi conserva timeout<=15s y HTTPS<=10s: hasta dos asociaciones
(30s) y una consulta(10s), más el coste acotado de inicialización/limpieza.

Cambio de ruta fuerza200 sin If-None-Match; siguientes consultas admiten304
si cache vigente y ETag válido. No se renueva expires_at por304. El modelo,
revisión y tiempo se validan con el parser M3.5. Identidad device debe ser la
misma para ambos bindings; tokens/CA pueden ser distintos. El Core debe aceptar
las credenciales de cada sitio dentro de sus límites de rotación, con scopes
explícitos. No es permiso para enviar telemetría laboral a CASA.

No hay continuidad instantánea dormido. Ante pérdida de red, radio apagada,
cache sólo vigente hasta expires_at; después OFFLINE y métricas ocultas. Backoff
retenido hasta tres fallos,60/120/240/300s para datos no vigentes; una consulta
por despertar. Se conserva navegación, BOOT corto/largo, PWR eléctrico,
framebuffer diff, full refresh y Power Manager. No nuevos GPIO o dependencias.

## Topología y candidatos

| Sitio | Decisión de preparación | Evidencia y pendiente |
| --- | --- | --- |
| CASA | `infrabadge-core`, Edge permanente operativo | HTTPS8443 restringido, salto local verificado al Core9443; ESP32 con DHCP reservado y origen /32 aprobado. `nas-01` conserva únicamente su rol NAS/collector |
| TRABAJO | `srv-linux` y `srv-mgmt`, sin selección definitiva | Requieren autorización organizacional y preflight de sólo lectura; no se accedió a estos candidatos |
| Core | Pi4 dedicado existente | HTTPS9443 privado; no publicar ese puerto a la LAN del badge ni cambiar SQLite |
| Fedora | Desarrollo/collector independiente | No interviene en las consultas cotidianas del ESP32 |

Por sitio: ESP32 Wi-Fi → edge HTTPS8443 en IP LAN exacta → HTTPS9443 sobre
Tailscale → Core. Usar el edge existente M3.2/M3.5 (`distributed.cli edge`),
sin bases de datos ni nuevo framework. Imagen fijada soporta ARM64/x86_64;
no se construyó/desplegó una nueva imagen real para estos hosts.

## TLS, privilegios y revocación

CA de laboratorio/sitio explícita, leaf con SAN DNS estable aprobado, fechas
válidas y renovación bajo la misma CA/SAN sin reprovisionar el badge. Si cambian
CA/nombre/token, preparar provisión privada autorizada; nunca heredar confianza
por SSID. Edge CASA y TRABAJO tienen identidades Core independientes, limitadas
al device y lectura v2; collector, reader y device conservan roles separados.
El edge no entrega ingestión/admin. Core no expuesto a Internet; sin subnet
routing amplio ni cambios automáticos de Grants. Acceso laboral y qué scopes
pueden salir del sitio requieren autorización organizacional antes del piloto.

Rotación: incorporar nuevo hash, entregar secreto por canal privado, verificar
ambos saltos, revocar anterior; nunca token en argv/CI/logs. Revocar sólo un edge
no rompe el otro (test TLS). Auditoría saneada de ruta lógica/resultado, sin
SSID, IP, MAC, device real, cabeceras o datos privados. El firmware sólo registra
resultados genéricos. No se instalaron agentes remotos ni se leyó inventario nuevo.

## Persistencia compatible

`ib_m2` y sus estructuras no cambian. El nuevo perfil sólo carga namespace
`ib_m36`, clave `bundle`, registro versión1/longitud/CRC y JSON limitado11000B.
La configuración pública tiene `policy` y `routes`; `bindings` y `seed_utc` son
privados. Es una única transacción nueva, sin borrar claves legacy ni inicializar
con erase. NVS es texto plano y no resiste extracción física. Se necesita margen
NVS para páginas/spare/registro: si no alcanza, falla sin auto-erase; no prometer
capacidad sólo a partir de longitud JSON. Verificar antes de futura provisión.

No hay migración automática ni fallback silencioso a ib_m2: sin bundle válido
muestra CONFIG/CLOCK. La semilla persistida NUNCA se usa como hora al arrancar.
Protocolo nuevo opt-in `IBPROV36`, sólo10s de cold boot, sin gesto BOOT ni puerto
en timer/manual deep wake. Paquete privado y UTC fresco se validan antes de
guardar. Los tests no escriben la placa; la provisión física CASA posterior fue autorizada y verificada por separado.
