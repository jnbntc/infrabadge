# M3.2 — SQLite, retención y recuperación

SQLite stdlib, un writer/proceso con flock exclusivo y lock de threads. Bases en
directorio local propio0700, archivos0600, sin symlinks. No NFS/SMB, Docker socket,
volúmenes compartidos entre hosts o base remota. Máximo128MiB,4096B/página;
busy timeout1s. Las transacciones son BEGIN IMMEDIATE/COMMIT/ROLLBACK y los valores
van por parámetros SQL. Un fallo de almacenamiento devuelve503, nunca ACK ficticio.

Se eligió **journal DELETE y synchronous FULL**, no WAL: carga pequeña y
serialización suficiente. Además, [SQLite documenta un fallo WAL-reset](https://www.sqlite.org/wal.html)
en versiones hasta3.51.2 bajo concurrencia específica. La versión stdlib local
observada es3.51.2; esta implementación rechaza journal WAL. Eso no sustituye
mantener el runtime/OS actualizado ni demuestra seguridad integral de SQLite.

## Migraciones y tablas

`store.MIGRATIONS` es el registro ordenado, `PRAGMA user_version` la versión.

1. Sitios/nodos y sus definiciones no secretas.
2. Última muestra/digest/evaluación, histórico, snapshots/revisión y piso de reloj.

Base nueva inicializa esquema2. Base existente antigua exige modo `migrate`
explícito; versión futura/corrupción se rechazan sin borrar/reemplazar original.
Cada migración es transaccional. No hay downgrade automático. Cambio futuro de
esquema requiere migración adicional, backup y pruebas antes de desplegar.

No se guardan tokens, sus digests de autenticación, passwords, certificados o
claves. El digest de contenido de muestra detecta corrupción accidental; no es
protección criptográfica frente a alguien que pueda modificar toda la base.

## Replay, reinicio y tiempo

La última collected_at/digest permanece aun al podar historial. Duplicado exacto
recibe el ACK M3 idempotente202, sin cambiar last_seen, salud o sesión. Misma
fecha con datos distintos o fecha anterior se rechaza409; intervalos demasiado
cortos429; datos futuros/caducados422. El segundo intento opt-in del collector
reenvía los mismos bytes dentro del timeout total; no hay cola histórica creciente.

Cada proceso usa una sesión nueva: últimas métricas/snapshots restaurados son
históricos. Una retransmisión idéntica tras reinicio no los vuelve frescos. Una
nueva muestra válida habilita evaluación nueva, sin heredar confirmaciones CPU
anteriores. Revisión del snapshot sigue siendo monotónica en la base conservada.
El piso UTC durable rechaza retroceso del reloj con503; no se reemplaza por RTC2056
ni por hora guardada como si fuera ahora. NTP confiable de Linux queda como
precondición operativa, no se configura automáticamente.

Restaurar un backup antiguo pierde watermarks posteriores a ese backup: la defensa
antireplay no puede reconstruir hechos ausentes del archivo. Coordinar corte,
rotación/identidades o esperar muestras posteriores al corte; no prometer antirollback
criptográfico. Un root o usuario comprometido puede leer/modificar datos locales.

## Retención y backup

Historial default60 muestras/nodo y24h; configurable1–240 y60s–7d. Poda durante
ingreso nuevo; si no hay tráfico, registros viejos pueden permanecer hasta la
siguiente escritura. Última muestra/watermark persisten como históricos. Hasta512
nodos históricos retirados; superar el límite exige archivo/migración deliberada.
La cota de páginas frena crecimiento físico, aunque borrar filas no reduzca el
archivo inmediatamente. No se ejecuta VACUUM periódico o daemon de mantenimiento.

Backup usa [SQLite backup API](https://www.sqlite.org/backup.html), con deadline10s
y validación de integridad. Puede leer el writer activo mediante una conexión
read-only; no copiar un archivo vivo con cp ni copiar sólo main de una base WAL.
Destino siempre nuevo y privado; fallar no sustituye el respaldo anterior.
Restore valida y crea otro destino nuevo; no pisa base actual ni arranca servicios.
Rotación/cifrado/custodia de backups requiere política del operador; no se instala
retención automática en el host. No guardar SQLite o backups en Git/CI.

Comandos offline/operativos preparados en [DEPLOYMENT](M3.2-DEPLOYMENT.md).
Pruebas de corrupción son fixtures temporales; no cortes físicos de energía.
