# M3.2 — transporte privado y límites de seguridad

Esta consolidación no consulta ni modifica hosts o redes. El piloto autorizado
previo sí instaló servicios nativos, amplió el firewall privado del central y
autorizó aparte NTP continuo en el nodo remoto: no afirmar que nunca hubo
cambios operativos. Las evidencias están en
[M3.2-PHYSICAL-VALIDATION](M3.2-PHYSICAL-VALIDATION.md). `grants.proposal.json`
es un documento **inerte**, no una policy válida para aplicar. Propone sólo
collector/edge→core TCP9443 con tags de rol nuevos por aprobar. No contiene
administradores, grupos reales, IPs, claves o nodos. No abre22/SSH, no subnet
routing, exit nodes, Funnel, Serve o permisos generales casa↔trabajo.

[Tailscale Grants](https://tailscale.com/docs/features/access-control/grants)
se combinan con permisos existentes: añadir una regla restrictiva no revoca un
allow-all anterior. El administrador debe revisar policy completa, asignación de
tags y tests positivos/negativos de puerto/identidad antes de autorizar. No se
ejecutaron tests reales de policy ni se certifica aislamiento de la tailnet.

## Fronteras

| Frontera | Controles | Límites |
| --- | --- | --- |
| Collector→core | Tailscale nodo-a-nodo + TLS CA/SAN/fecha + token exclusivo + scope nodo | Tailscale no sustituye TLS ni autorización organizacional |
| ESP32→edge | HTTPS LAN, token dispositivo, método/ruta/Host/ETag acotados | ESP32 no ejecuta Tailscale; resolución local requiere preflight |
| Edge→core | HTTPS fijo, CA explícita, doble identidad edge/dispositivo, scopes | Edge comprometido ve bearer en tránsito; no es un túnel de comandos |
| Inventario | Reader con sitios explícitos; sin API de edición | La config del operador es autoridad; no descubre equipos |
| SQLite | Transacciones, antireplay durable, históricos explícitos, permisos | Sin cifrado propio; backup antiguo no conserva eventos posteriores |
| Runtime | Rootless, RO, sin capacidades, NNP, límite16 requests/conexiones | Quotas no equivalen a defensa volumétrica ni rate limit de handshakes |

Ingreso8KiB/deadline5s y cabeceras8KiB; credenciales hasta103B incluyendo Bearer.
Cuota global240/min burst40, collector6/min burst2, dispositivo12/min burst6.
Edge global120/min burst20, dispositivo12/min burst6; upstream16 conexiones,
deadline total6s y body4096B. Mapas sólo para identidades configuradas; no crecen
con identidades del atacante. No redirects/proxy ambiental/URL arbitraria.
El guard de interfaz/ruta/lease de M3.1 no está portado al edge: es un gate
antes de cualquier exposición LAN, aunque el core privado ya tenga un firewall
de origen específico. Ver [comparación](M3.2-INTEGRATION-AUDIT.md).
Access logs deshabilitados; errores genéricos sin payloads, paths, tokens o IPs.

## Trabajo y tailnets separadas

No se asume que ambos sitios compartan tailnet ni que el trabajo permita exportar
telemetría al domicilio. Mantener trabajo deshabilitado hasta aprobación de
responsables sobre métricas, destino, retención, credenciales y acceso desde casa.
No instalar agents/exporters ni inspeccionar otros equipos automáticamente.

Si tailnets separadas, Grants no crea conectividad entre ellas. Opciones por
aprobar: enlace HTTPS servidor-a-servidor autorizado, mecanismos de compartición
admitidos por ambas organizaciones o un core separado bajo control laboral.
En ese último caso ya no existe una fuente global única: no declarar agregación
casa/trabajo como disponible. Si no hay autorización, limitar core a sitios
permitidos y mantener trabajo deshabilitado; no sortearlo con rutas o Funnel.

## Confianza TLS y movilidad

CA privada común bajo custodia de firma externa al gateway; leafs distintos por
edge con SAN del origen autorizado. No copiar claves privadas de leaf entre sitios.
El núcleo Linux puede resolverse por MagicDNS; el ESP32 necesita DNS local propio
o provisión explícita de un origen accesible. Sin multi-SSID nuevo en firmware.
Rotar CA/token/UTC del dispositivo requiere aprobación USB aparte; no se modifica
NVS automáticamente. La limitación de la CA M3 sin clave de firma disponible
sigue pendiente antes de migrar confianza de producción.

## Auditoría de dependencias

OSV sobre25 versiones públicas del lock detectó GHSA-6q48-6c7w-9gw2 y su alias
PYSEC-2026-4320 para certifi. Se fija **certifi2026.10.19** con hashes oficiales.
[Aviso del mantenedor](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2).
La segunda consulta de las25 versiones del lock corregido no devolvió avisos
OSV (2026-10-21); ese resultado no garantiza ausencia de vulnerabilidades. Runtime usa CA explícita; la
corrección no instala nada en M3 operativo ni modifica PR5. La revisión previa
de M3 ocurrió antes de publicarse el aviso: no se reutiliza como scan actual.

La consulta no cubre SO base, pip vendorizado, BuildKit, SDK o todos los problemas
de stdlib. Versiones/digests fijados no son un certificado de seguridad. Revisar
esos componentes antes de publicar imágenes operativas y mantener una política
de actualizaciones. Licencia global original sigue pendiente; avisos upstream
se conservan. No se promete cifrado NVS o resistencia a extracción física.
